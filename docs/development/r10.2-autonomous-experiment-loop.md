# Agonionce R10.2 — Autonomous Experiment Loop

## Result

R10.2 makes evidence-driven experiments the center of the next-decision cycle
without moving execution authority into the Experiment Layer. After each
analyzed Observation, Agonionce builds a bounded Research Context, generates
multiple Hypothesis candidates, ranks them deterministically, and exposes the
highest-value experiment goal to the existing Planner.

```text
Observation
  -> Analyzer / Intelligence update
  -> bounded Research Context
  -> Hypothesis candidates
  -> deterministic prioritization
  -> next experiment recommendation
  -> Planner experiment_action
  -> ExperimentOrchestrator
  -> ToolRuntime / Policy / Approval / Sandbox
  -> Evidence / Evaluation
  -> Intelligence + Domain feedback
  -> next Research Context
```

The loop selects what should be investigated next. It cannot select a Tool
backend, invoke an Executor, open a network connection, or bypass the existing
Planner and controlled execution path.

## Architecture

R10.2 extends `agent/intelligence/experiment/runtime/` with:

- `research.py`: checkpoint-safe Research Context, multi-source
  `HypothesisCandidate`, Domain reasoning adapter, deterministic generator, and
  prioritizer;
- `feedback.py`: evidence-driven Hypothesis, failed-attempt, and Domain context
  updates;
- `loop.py`: the `AutonomousExperimentLoop` coordinator and next-decision
  history;
- the existing `orchestrator.py`: optional loop feedback and post-analysis
  advancement while retaining no Tool or Executor dependency;
- the existing `experiment_runtime.py`: schema-versioned loop state and
  feedback persistence.

The AgentRuntime protocol, Planner protocol, ToolRuntime, PolicyEngine,
ApprovalManager, Sandbox layer, and R6 Experiment lifecycle remain intact.

## Decision Flow

The Research Context contains only bounded data:

- current Observation ID, objective, and Analyzer summary;
- Intelligence counts and up to five open questions;
- Domain name, phase, goal, and expected observations;
- up to five recent Experiment runtime outcomes;
- up to five sanitized Experience records.

It excludes raw Tool arguments, unbounded outputs, credentials, cookies,
secrets, and executable behavior. The next Planner context contains ranked
candidates with an existing Hypothesis ID, suggested goal, expected observable
result, score reasons, and Experience influence IDs.

The Planner still creates the typed `experiment_action`. It chooses a
registered Tool and arguments, which are then validated and authorized by the
ordinary execution boundary. A recommendation is not execution permission.

## Hypothesis Lifecycle

`Hypothesis` now records:

- `source`: `ANALYZER`, `INTELLIGENCE`, `DOMAIN_RUNTIME`, `EXPERIENCE`, or
  `MANUAL`;
- numeric or enum confidence;
- `priority`: `LOW`, `MEDIUM`, or `HIGH`;
- provenance-bearing `related_artifacts`;
- sanitized `experience_influence` IDs.

Candidates can originate from:

1. Analyzer `hypothesis` suggestions;
2. existing OPEN IntelligenceState hypotheses and questions;
3. declarative Domain phase evidence gaps;
4. bounded, sanitized retrieved Experience.

Candidates are normalized and deduplicated. A terminal Hypothesis is not
silently recreated. Materialized candidates enter the per-challenge
IntelligenceState; retrieved Experience itself remains separate global memory.

Evaluation feedback is deterministic:

| Evaluation | Hypothesis feedback | Additional record |
| --- | --- | --- |
| `SUPPORTED` | status becomes `SUPPORTED`; confidence increases, capped below automatic confirmation | Domain feedback |
| `CONTRADICTED` | evidence-backed status becomes `REJECTED` | sanitized per-run `FailedAttempt` and Domain feedback |
| `INCONCLUSIVE` | status remains `OPEN`; confidence is reduced slightly | pending follow-up suggestion and Domain feedback |

`SUPPORTED` is not `CONFIRMED`. No Evaluation solves a challenge, submits a
flag, or changes authorization scope.

## Experiment Prioritization

The first prioritizer is deterministic and testable. Its score considers:

- explicit Hypothesis priority;
- confidence;
- estimated evidence value;
- relevance supplied by the current Domain phase;
- matching retrieved Experience;
- a penalty for repeated failed or contradicted experiments bound to the same
  Hypothesis.

Score reasons are persisted and shown to the Planner. The system does not hide
why one candidate was selected over another. The prioritizer proposes an
experiment goal and expected observation only; it does not generate payloads
or Tool calls.

## Domain Integration

`DomainExperimentAdapter` reads the existing declarative Domain runtime. For
Web it can propose:

- RECON endpoint baseline characterization;
- ANALYSIS/EXPLOITATION parameter behavior comparison.

Other Domain phases receive a generic evidence-gap candidate based on their
declared `expected_observations`. This interface contains no `tool_name`, Tool
arguments, payloads, or network behavior.

After Evaluation, the Domain runtime stores a maximum of ten compact feedback
records in `DomainRuntimeState.details["experiment_feedback"]`. This lets the
next Domain Context reflect supported, contradicted, or inconclusive research
without coupling Domain Runtime to execution.

## Experience Integration

The existing `ExperienceRetriever` remains the only source of cross-challenge
memory. R10.2 uses its already bounded, sanitized output to:

- suggest a generic pattern check;
- influence matching Analyzer, Intelligence, or Domain candidates;
- add a small, explainable priority bonus;
- record only opaque Experience IDs on the current Hypothesis and decision.

R10.2 never writes `ExperienceStore`, approves an ExperienceCandidate, copies
current challenge secrets into global memory, or modifies a Skill.

## Checkpoint and Recovery

`experiment_runtime.json` schema version 2 preserves:

- active Hypothesis IDs;
- ranked Hypothesis candidates;
- pending R10.1 runtime Experiments;
- Experiment history and Evaluation results;
- feedback application state;
- inconclusive follow-up suggestions;
- bounded last Research Context;
- loop iteration and decision history.

Schema version 1 from R10.1 remains loadable. Loop advancement is idempotent by
source step, candidate identities are deterministic, and feedback records an
explicit `feedback_applied` boundary. A durably completed Experiment is not
executed again on recovery.

## CLI

```bash
python main.py experiment loop
python main.py experiment loop --checkpoint <checkpoint-directory>
python main.py experiment history
python main.py experiment history --checkpoint <checkpoint-directory>
python main.py hypothesis list
```

`experiment loop` shows the iteration, active and pending counts, ranked
candidates, sources, scores, next goals, and Experience influence.
`experiment history` shows runtime status, Evaluation, Evidence count, and
feedback status. `hypothesis list` adds source, priority, and provenance.

## Demo

Run:

```bash
python demos/r102_autonomous_experiment_loop.py
```

The demo uses an authorized fake-local Web challenge and a fake Tool in
`autonomous_local` mode:

```text
Observation: local id parameter
  -> Analyzer + Domain + Experience candidates
  -> ranked Hypothesis
  -> Planner experiment_action
  -> fake Tool through ToolRuntime and PolicyEngine
  -> Artifact-backed Evidence
  -> SUPPORTED Evaluation
  -> Hypothesis and Domain feedback
  -> next research decision
```

It restores the version-2 checkpoint and prints:

```text
LOCAL_AUTONOMOUS_EXPERIMENT_LOOP_OK
```

The demo opens no network connection and performs no exploitation.

## Security Boundary

R10.2 does not add scanners, payload generation, exploit automation, public
target requests, automatic flag submission, Skill rewriting, Global Experience
writes, knowledge graphs, embeddings, model training, or multi-agent behavior.

Every proposed experiment still requires the Planner's typed ActionProposal
and the existing Tool schema, ToolRuntime, PolicyEngine, ApprovalManager,
execution mode, workspace, Sandbox, ArtifactStore, audit, and budget controls.

## Future Extension

Domain-specific autonomous reasoning can extend the declarative candidate
interface with richer evidence-value estimates and test goals. It must not put
Tool calls, shell commands, payloads, or approval decisions into Domain Runtime
or Skill content. Future semantic Evaluation requires a separate reviewed
contract and cannot erase contrary Evidence.

## Remaining Risks

- Candidate generation and Evaluation are deterministic rules and cannot
  understand complex semantics.
- A Domain hint can be low value; bounded scores and Planner review reduce but
  do not eliminate wasted experiments.
- Feedback updates current-challenge state automatically, but `SUPPORTED`
  deliberately remains distinct from `CONFIRMED` and challenge completion.
- Experiments remain single-ToolCall; multi-step experimental protocols are not
  implemented.
- The pre-`tool_result` at-least-once crash window and per-file checkpoint
  atomicity limitation remain.
- No automatic learning, Skill evolution, knowledge graph, Global Experience
  write, exploit automation, or public-target autonomy is implemented.
