# Agonionce R9.2 — Sandbox Runtime Foundation

## Result

R9.2 adds an independent, fail-closed Docker Sandbox Layer for authorized local
CTF execution. It does not change the AgentRuntime, Planner, Experiment, or
PolicyEngine protocols and adds no vulnerability knowledge, payload database,
scanner, exploit engine, browser automation, or remote-target capability.

The controlled execution path is:

```text
Planner
  -> ToolCall: sandbox_python
  -> ToolRuntime JSON Schema validation
  -> PolicyEngine execution-mode and workspace-scope decision
  -> ApprovalManager when policy requires it
  -> SandboxPythonTool
  -> SandboxManager
  -> SandboxPolicy
  -> DockerBackend
  -> network-disabled container
  -> execution Artifact
  -> ToolResult and Tool audit
```

Tools never invoke Docker directly. `SandboxManager` owns lifecycle
coordination and is the only production facade exposed to `sandbox_python`.

## Architecture

The new Sandbox Layer is contained under `agent/sandbox/`:

- `models.py` defines `SandboxSpec`, `SandboxMount`, environment availability,
  normalized results, and sandbox-specific errors.
- `policy.py` validates the fixed workspace mount contract and the disabled
  network boundary independently of Tool policy.
- `docker.py` is the only Docker CLI adapter. It creates, attaches, enforces a
  timeout, and removes one disposable container without using a shell.
- `manager.py` validates a spec, coordinates the backend lifecycle, and reports
  cleanup failure as an execution failure.

This is an Environment/Execution Layer boundary. It does not become an agent
brain, Planner extension, alternate ToolRuntime, or authorization source.

## SandboxSpec

`SandboxSpec` supports the requested resource and isolation controls:

| Field | R9.2 behavior |
| --- | --- |
| `image` | Non-empty local image reference. Docker image pulling is never automatic. |
| `network` | Must be `none`. Host, bridge, and external networks are rejected. |
| `cpu_limit` | Positive, capped at 4 CPUs; default 1 CPU. |
| `memory_limit` | 32 MiB through 2 GiB; default 256 MiB. |
| `timeout` | 0.1 through 300 seconds; default 30 seconds. |
| `mounts` | Exactly the three active workspace directories and no others. |

The Docker backend also applies:

- a read-only container root filesystem;
- the current non-root host UID/GID so `work` and `output` remain usable (root
  hosts fall back to UID/GID 65534);
- all Linux capabilities dropped;
- `no-new-privileges`;
- PID limit 64;
- file descriptor limit 256;
- a 64 MiB `noexec,nosuid` temporary filesystem;
- an isolated Python environment with bytecode writes disabled.

The backend accepts only a typed command argument list and internally builds
all Docker flags. It uses no shell and accepts no Planner-controlled Docker
option. The availability check accepts only a local `unix://` Docker endpoint
(or a local Windows `npipe://` endpoint); remote `tcp://` and `ssh://` Docker
contexts fail closed.

## Workspace Mount Contract

Only these bindings are legal:

| Host workspace scope | Container path | Access |
| --- | --- | --- |
| current challenge `input/` | `/workspace/input` | read-only |
| current challenge `work/` | `/workspace/work` | read-write |
| current challenge `output/` | `/workspace/output` | read-write |

`SandboxPolicy` resolves and compares every mount source with the current
`ExecutionContext`. A mount must be the exact declared scope directory, must
exist, and must remain under that challenge workspace. Arbitrary host paths,
the Docker socket, alternate container destinations, duplicate targets, and a
writable input mount are rejected before container creation.

Workspace URIs remain the Planner-facing contract. For example,
`workspace://input/solve.py` becomes `/workspace/input/solve.py` only after the
ordinary ToolRuntime filesystem policy and the Tool resolver both accept it.
Host paths are not written to ToolResult metadata or execution artifacts.

## Docker Lifecycle

For every execution, `SandboxManager` performs:

```text
validate SandboxSpec
  -> verify Docker client and daemon
  -> verify the image already exists locally
  -> docker create
  -> docker start --attach with hard timeout
  -> docker rm --force in finally
  -> normalized SandboxResult
```

The backend does not use `docker run` as an opaque shortcut because explicit
create, attach, and cleanup stages make the lifecycle testable. If execution
times out, the result has exit code 124 and the `finally` cleanup forcibly
removes the container. Cleanup failure changes the overall result to failure
so a leaked container cannot be silently reported as success.

## `sandbox_python` Tool

The Tool accepts only:

```json
{
  "script": "workspace://input/solve.py",
  "args": ["fixture"],
  "timeout": 10
}
```

The script must be a `.py` file in `input` or `work`. The Tool fixes the image,
network mode, CPU, memory, mounts, Python executable, and isolated Python flag;
the Planner cannot change them.

`sandbox_python` declares `autonomous_allowed=true`, so the existing
PolicyEngine permits it in `autonomous_local` after schema and workspace checks.
Legacy `python` and `bash` remain registered for compatibility with manual and
supervised operation, retain `autonomous_allowed=false`, and are denied in
`autonomous_local`.

## Artifact Integration

Every completed sandbox process writes one private JSON artifact under:

```text
workspace/<challenge-id>/output/sandbox/
```

The artifact contains:

- stdout;
- stderr;
- exit code;
- duration;
- timeout status;
- cleanup status;
- image, network, CPU, memory, timeout, and container-side mount metadata.

ToolRuntime registers it in the existing `ArtifactStore` with artifact type
`sandbox_execution`. Host mount paths are excluded from the payload. The
ordinary Tool audit still records the run, step, arguments hash, policy result,
execution mode, timing, redacted output, and artifact reference.

## CLI Usage

Run the read-only environment check:

```bash
python main.py sandbox check
```

It checks the Docker CLI, daemon, and the local
`python:3.12-alpine` image. The command never starts Docker and never pulls an
image. Any missing prerequisite returns exit code 1.

## Demo

The real local Docker demonstration is:

```bash
python demos/r92_local_sandbox.py
```

It creates a temporary authorized fake challenge, selects
`autonomous_local`, submits `sandbox_python` through ToolRuntime and the
existing PolicyEngine, runs a deterministic script in Docker with networking
disabled, checks the registered artifact, and prints:

```text
LOCAL_SANDBOX_OK
```

The Docker daemon must already be running and the default image must already
exist locally. The demo fails closed instead of starting the daemon or pulling
an image.

## Security Boundary

R9.2 explicitly forbids:

- privileged containers;
- host networking or any enabled container network;
- Docker or Podman socket mounts;
- arbitrary host filesystem mounts;
- root execution, added capabilities, or privilege escalation;
- automatic image pulling;
- direct Docker access from Planner or a Tool;
- autonomous use of the legacy host `python` or `bash` Tools;
- remote target automation.
- remote or unresolved Docker daemon contexts.

Image availability and Docker availability are environmental capability only;
they do not establish challenge authorization. ToolRuntime, PolicyEngine,
ApprovalManager, workspace isolation, ArtifactStore, and audit controls remain
in force outside the container.

## Validation

The required validation commands are:

```bash
source .venv/bin/activate
pytest -q
python -m pip check
python -m compileall .
python main.py --help
python main.py sandbox check
python demos/r92_local_sandbox.py
git diff --check
git status --short
```

Docker lifecycle tests use an injected deterministic command runner. They
cover client/daemon availability, exact workspace mounts, disabled networking,
resource flags, timeout exit code, forced cleanup, and prohibited Docker
options without requiring a daemon or public network. Tool integration tests
use an injected backend and verify policy flow plus persisted Artifact content.

Final validation from the project virtual environment:


For the real local validation, Docker Desktop was started and the official
`python:3.12-alpine` image was pulled manually after the check reported it
missing. The Agonionce backend itself did not start Docker or pull an image.

## Remaining Risks

- Docker daemon security and image provenance remain operator
  responsibilities; R9.2 does not pull, sign, scan, or pin an image digest.
- Docker Desktop uses its own VM on macOS; Linux deployments depend on the
  local Docker daemon's isolation configuration.
- R9.2 does not yet apply a custom seccomp/AppArmor profile.
- Captured stdout and stderr are timeout-bounded but do not yet have a byte
  quota.
- Writable `work` and `output` mounts can retain files produced before a
  timeout; those effects are intentionally contained in the challenge
  workspace but are not transactional.
- Container execution remains local-only. Remote Docker contexts and remote
  targets are outside the R9.2 authorization boundary.
- R9.2 adds no automatic Experiment execution, exploit capability, or
  vulnerability-specific reasoning.
