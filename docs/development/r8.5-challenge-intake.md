# Agonionce R8.5 Completion Report

## Result

R8.5 adds a Challenge Intake Layer that turns explicit local user input into a
validated `ChallengeManifest`, a contained workspace, an existing
`ChallengeSpec`, and an ignored per-challenge experience folder. Users no
longer need to calculate a challenge ID, create workspace directories, or copy
attachments and source trees manually.

The Intake Layer does not execute challenge content and grants no Tool or
network authority. `AgentRuntime`, the Planner protocol, ToolRuntime,
PolicyEngine, and the Experiment Layer are unchanged.

## Challenge Intake Architecture

```text
User Input
  |
  v
ChallengeImporter
  |
  +-- Challenge validation and sensitive-input rejection
  +-- ChallengeWorkspaceBootstrap -> WorkspaceManager containment
  +-- ArtifactStore input binding
  +-- ChallengeExperienceManager
  |
  v
ChallengeManifest
  |
  +-- workspace/<challenge-id>/
  +-- experiences/challenges/<challenge-name>/
  |
  v
Question -> ChallengeSpec -> existing AgentRuntime
```

The new code lives under `agent/challenge/`:

- `models.py` owns the portable `ChallengeManifest` and unified ID generation.
- `validator.py` owns domain, URL, relative-path, secret, and sensitive-file
  validation.
- `workspace.py` stages explicit inputs through the existing
  `WorkspaceManager` and registers imported files in `ArtifactStore`.
- `manifest.py` persists and retrieves ignored `challenge.json` records.
- `importer.py` coordinates validation, workspace bootstrap, and experience
  initialization without executing a Tool.
- `experience.py` creates per-challenge records and binds completed run data.
- `writeup.py` renders a deterministic template; it makes no LLM call.

## Challenge Flow

```text
Name + Description + Domain + URL + Attachments + Source
  -> validate authorization metadata
  -> generate <name>-<YYYYMMDD>-<hash>
  -> create isolated workspace
  -> copy attachment into input/
  -> copy one source directory's contents into input/source/
  -> register imported files as challenge-input artifacts
  -> write ChallengeManifest
  -> create per-challenge experience templates
  -> solve --challenge <id>
  -> existing Question -> ChallengeSpec bridge
  -> existing runtime and checkpoint flow
  -> bind run snapshot under runs/run-NNN/
```

The ID includes fresh entropy in addition to the name and timestamp. Repeated
runs use the same imported ID and allocate `run-001`, `run-002`, and later run
folders; independent imports cannot silently reuse a content-derived
workspace. Re-creating an already imported challenge name is rejected with the
existing ID so the user can start another run safely.

## CLI Usage

Interactive intake:

```bash
python main.py challenge create
```

Non-interactive local intake:

```bash
python main.py challenge create \
  --name easy_sqlite \
  --description "Local authorized web challenge" \
  --domain web \
  --url http://127.0.0.1:5000 \
  --attachment challenge.zip \
  --source source/
```

A UTF-8 question file is also accepted:

```bash
python main.py challenge create \
  --name easy_sqlite \
  --description-file challenge.txt \
  --domain web
```

Catalog and launch commands:

```bash
python main.py challenge list
python main.py challenge show <challenge-id>
python main.py solve --challenge <challenge-id> --manual --no-resume
```

`--attachment` and `--source` may be repeated. Intake defaults to the current
directory as the authorized source root; `--source-root` can narrow it further.
Custom workspace and experience roots are explicit CLI options. A custom
experience root must also be passed to `solve --challenge-root`.

## Workspace Layout

```text
workspace/
└── easy_sqlite-20260821-a91fd3/
    ├── input/
    │   ├── challenge.zip
    │   └── source/
    │       └── app.py
    ├── work/
    ├── output/
    └── logs/
        └── artifacts.json
```

Archives remain opaque files: they are copied but never extracted or executed.
One imported source directory is flattened into `input/source/`; multiple
source inputs retain their basenames to prevent collisions.

## Experience Layout

R8.5 separates reusable global R7 memory from private per-challenge records:

```text
experiences/
├── global/
│   └── experience.json
└── challenges/
    └── easy_sqlite/
        ├── challenge.json
        ├── description.md
        ├── artifacts/
        │   ├── imported.json
        │   └── run-001/
        ├── intelligence.json
        ├── experiments.json
        ├── analysis.md
        ├── writeup.md
        ├── lessons.md
        └── runs/
            └── run-001/
                ├── run.json
                ├── checkpoint/
                ├── artifacts/
                └── result.md
```

`ChallengeExperienceManager` performs binding only. It does not extract global
experience, rewrite Skills, call an LLM, or promote Intelligence conclusions.
Existing local configuration that explicitly points R7 memory at
`experiences/experience.json` remains supported; the new unconfigured/public
default is `experiences/global/experience.json`.

The generated `writeup.md` contains these empty sections:

```text
Overview
Recon
Analysis
Experiments
Evidence
Solution
Flag
Lessons Learned
```

It is a scaffold, not an automatically generated final writeup.

## Security Boundary

Challenge intake is a local filesystem preparation capability, not a Tool
execution path. It enforces the following rules before copying:

- Every source must resolve beneath the explicit `source_root`.
- Destination paths are resolved through `WorkspaceManager` and must remain in
  the selected challenge workspace.
- Existing workspace data cannot be re-imported as user input.
- Symbolic links are rejected at the input root and inside directory trees.
- `.env`, `config.json`, private-key files, and common credential files are
  rejected by name.
- Concrete flag-shaped answers, API-key-shaped values, and secret assignments
  are rejected from manifest text.
- URLs containing user information are rejected.
- Files are copied only; no script, archive, Dockerfile, or source file is
  executed automatically.
- A stored URL does not bypass the existing loopback HTTP policy, ToolRuntime,
  PolicyEngine, or ApprovalManager.

`challenge.json`, workspace data, per-challenge runs, checkpoints, and
artifacts live under ignored runtime directories and must not be committed.

## Remaining Risks

- Challenge names are unique within the default per-challenge catalog; users
  should reuse the existing ID for another run rather than re-importing it.
- Intake does not inspect archive contents and never extracts them. A later
  archive inspection feature would require its own bounded validation design.
- Per-challenge writeups and lessons are templates only; no Writer is present.
- Run binding occurs after the existing runtime returns and checkpoint save
  succeeds. A process killed before that point can leave a RUNNING run folder.
- Public targets remain denied by existing execution policy even when a URL is
  present in a manifest.
- No Web UI, MCP, remote Tool, platform upload, scanner, exploit generator,
  payload database, automatic learning, or Skill rewriting is implemented.
