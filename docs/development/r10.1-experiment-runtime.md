# Agonionce R10.1 — Experiment Runtime Integration

## Result

R10.1 integrates the existing R6 Hypothesis, Experiment, and Evidence models
into the real AgentRuntime step lifecycle. It preserves the existing Planner
protocol, ActionProposal action list, ToolRuntime, PolicyEngine, ApprovalManager,
Sandbox, Analyzer, and Intelligence update boundaries.

The runtime path is now:

```text
Planner
  -> ActionProposal
  -> Decision Router
     +-- normal_action -> unchanged Tool execution path
     +-- experiment_action
           -> ExperimentOrchestrator.prepare
           -> OPEN Hypothesis binding or creation
           -> Experiment PROPOSED -> RUNNING
           -> ToolRuntime / Policy / Approval / Sandbox as applicable
           -> Observation with stable observation_id
           -> EvidenceFactory
           -> ExperimentEvaluator
           -> experiment_result checkpoint
           -> Analyzer
           -> Intelligence update
           -> bounded evaluation context for the next Planner decision
```

`ExperimentOrchestrator` does not own an Executor, Tool registry, network
client, or sandbox backend. AgentRuntime still sends the unchanged
`ActionProposal` through its injected Executor. The Orchestrator only prepares
reasoning state before that call and consumes the returned Observation after
controlled execution.

## Architecture

R10.1 adds `agent/intelligence/experiment/runtime/`:

- `experiment_runtime.py` owns persistent execution records, lifecycle status,
  evaluation records, pending indexes, and transition validation.
- `orchestrator.py` implements experiment decision routing, Hypothesis and
  Experiment binding, idempotent result handling, and checkpoint recovery.
- `evaluator.py` owns provenance-enforcing `EvidenceFactory` and deterministic
  `ExperimentEvaluator` logic.

The R6 `ExperimentManager` remains the owner of IntelligenceState lifecycle
mutations and still cannot execute a Tool. R10.1 composes it rather than
replacing it.

Two status types remain intentionally separate:

| State | Meaning |
| --- | --- |
| R6 `ExperimentStatus` | Intelligence history: `PROPOSED`, `RUNNING`, `SUCCESS`, `FAILED`. Success means the controlled experiment executed with evidence. |
| R10.1 `ExperimentRuntimeStatus` | Runtime lifecycle: `CREATED`, `RUNNING`, `COMPLETED`, `FAILED`. |
| `ExperimentEvaluationStatus` | Evidence interpretation: `SUPPORTED`, `CONTRADICTED`, `INCONCLUSIVE`. |

A successful ToolResult does not itself support a Hypothesis. A completed
Experiment may be `CONTRADICTED` or `INCONCLUSIVE`. Evaluation remains separate
from Evidence and never automatically confirms or rejects the Hypothesis.

## Planner Extension

Legacy Planner JSON remains valid and defaults to:

```json
{
  "decision_type": "normal_action",
  "objective": "inspect local data",
  "reasoning_summary": "one bounded action",
  "actions": [
    {
      "call_id": "call-1",
      "tool_name": "workspace_read_text",
      "arguments": {"path": "workspace://input/challenge.txt"}
    }
  ]
}
```

An experiment decision uses exactly one ToolCall:

```json
{
  "decision_type": "experiment_action",
  "objective": "verify endpoint behavior",
  "reasoning_summary": "test one observable response property",
  "hypothesis_id": "hypothesis-existing-id",
  "experiment_goal": "verify endpoint behavior",
  "expected_result": "response changed",
  "action": {
    "call_id": "call-1",
    "tool_name": "http_request",
    "arguments": {}
  }
}
```

If `hypothesis_id` is omitted, `hypothesis_statement` is required and the
Orchestrator creates one OPEN Hypothesis with the supplied domain and bounded
confidence. An unknown or non-OPEN Hypothesis ID fails closed. The aliases
`normal` and `experiment` are accepted at the JSON compatibility boundary and
normalized to the canonical values.

`ActionProposal.actions` and the Planner protocol are unchanged. The optional
`decision_type` field defaults to `normal_action`, and experiment-specific data
is stored in structured proposal metadata.

## Experiment Runtime

For an `experiment_action`, the Orchestrator performs:

```text
validate experiment intent
  -> bind/create OPEN Hypothesis
  -> create R6 Experiment
  -> create runtime record as CREATED
  -> transition both records to RUNNING
  -> return the original ActionProposal to the ordinary Executor
```

After execution it:

```text
Observation
  -> provenance-complete Evidence records
  -> actual_result derived from ToolResult only
  -> close R6 Experiment as SUCCESS or FAILED
  -> deterministic Evaluation
  -> attach Evidence IDs to the still-reviewable Hypothesis
  -> close runtime record as COMPLETED or FAILED
```

Experiments are single-action in R10.1. This keeps one hypothesis test bound to
one policy decision, one Tool audit sequence, and one stable observation.

## Evidence Flow

`EvidenceFactory` accepts a `ToolResult` only when all provenance is present:

- `experiment_id`;
- `hypothesis_id`;
- stable `observation_id`;
- Tool name and call ID in `source`;
- at least one ArtifactStore reference.

The Evidence observation is a bounded representation of ToolResult success,
exit code, stdout, stderr, and error. It never contains a conclusion field.
Missing Artifact provenance raises `EvidenceProvenanceError`; the Orchestrator
records no untraceable Evidence, closes the Experiment as failed, and returns
an `INCONCLUSIVE` evaluation.

Every runtime Evidence reference is cross-validated on checkpoint load against
the corresponding Hypothesis, Experiment, Observation ID, and non-empty
Artifact references.

## Evaluation

`ExperimentEvaluator` is deterministic and does not call an LLM. It returns:

- `SUPPORTED` when provenance-complete successful Evidence matches the material
  terms of the expected observable result;
- `CONTRADICTED` when Evidence contains an explicit contrary outcome;
- `INCONCLUSIVE` for failed execution, missing Evidence, or insufficiently
  decisive Evidence.

This first evaluator is deliberately conservative. It stores a rationale and
Evidence IDs separately from Evidence. The Hypothesis remains OPEN for human or
future governed review.

The bounded Planner experiment context now includes recent runtime status,
Evidence count, evaluation status, and rationale so the next decision can avoid
blind repetition without turning an Evaluation into execution authority.

## Checkpoint and Recovery

Every runtime checkpoint now optionally includes:

```text
experiment_runtime.json
```

Its schema stores:

- run and challenge identity;
- current Experiment runtime records;
- pending Experiment IDs;
- Hypothesis and Experiment bindings;
- lifecycle status;
- Observation and Evidence IDs;
- Evaluation results;
- the normalized Planner proposal and fingerprint;
- recoverable ToolResult snapshots.

The step checkpoint adds the durable `experiment_result` stage between
`tool_result` and `analyzer_result`:

```text
planner_proposal
  -> tool_approval
  -> tool_result
  -> experiment_result
  -> analyzer_result
  -> experiment_update
  -> step_complete
```

On recovery:

- a RUNNING record after `tool_result` creates Evidence and Evaluation without
  re-executing the Tool;
- a COMPLETED/FAILED record restores its persisted ToolResult and proceeds to
  Analyzer;
- repeated completion calls are idempotent and cannot add duplicate Evidence;
- an experiment proposal persisted before the latest `step.json` is recovered
  from `experiment_runtime.json` by step ID and proposal fingerprint.

As in R9.1, a process crash after a Tool side effect but before any durable
ToolResult remains an at-least-once window. R10.1 guarantees that a durably
completed Experiment is not executed again.

## CLI

Existing commands remain available:

```bash
python main.py experiment list
python main.py hypothesis list
python main.py evidence list
```

R10.1 adds:

```bash
python main.py experiment status
python main.py experiment status --checkpoint <checkpoint-directory>
```

The status table displays Hypothesis ID, Experiment ID, runtime status,
Evidence count, and Evaluation. Pre-R10.1 checkpoints without
`experiment_runtime.json` remain readable and display their legacy R6 status.

## Demo

Run:

```bash
python demos/r101_experiment_runtime.py
```

The demo uses only an authorized fake-local challenge and fake Tool. It runs in
`autonomous_local`, produces an Artifact through ToolRuntime, passes the
existing PolicyEngine, generates provenance-complete Evidence, evaluates it as
`SUPPORTED`, preserves the Hypothesis as OPEN for review, restores the runtime
checkpoint, and prints:

```text
LOCAL_EXPERIMENT_RUNTIME_OK
```

It opens no network connection, performs no exploitation, and submits no flag.

## Security Boundary

R10.1 does not authorize or implement:

- automatic exploitation or payload generation;
- public-network requests or expanded target scope;
- automatic Flag submission;
- Skill modification;
- Global Experience writes;
- automatic Hypothesis confirmation or rejection;
- direct Tool, Docker, shell, or network access from the Experiment Layer.

Every experiment action remains subject to Tool schema validation,
PolicyEngine, ApprovalManager, execution mode, workspace isolation, Sandbox
requirements, ArtifactStore, Tool audit, runtime budgets, and human review.

## Remaining Risks

- Evaluation uses conservative lexical rules and cannot understand complex
  semantic relationships; human review remains mandatory.
- Tools that do not produce an Artifact cannot create R10.1 Evidence and yield
  an inconclusive failed Experiment record.
- R10.1 permits exactly one ToolCall per Experiment; multi-action experimental
  protocols are not implemented.
- The pre-`tool_result` at-least-once crash window remains.
- Checkpoint files use atomic per-file replacement, not a filesystem-wide
  transactional snapshot.
- No automatic learning, Skill evolution, Global Experience write, knowledge
  graph, multi-agent execution, or exploit automation is implemented.
