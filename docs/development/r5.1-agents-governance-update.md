# R5.1 AGENTS.md Architecture Governance Update

## 1. Changes

R5.1 replaces the root contributor notes with an engineering constitution for
all future Agonionce development. The new `AGENTS.md` defines project authority,
identity, architectural ownership, execution boundaries, authorization rules,
extension workflow, validation requirements, repository hygiene, and
non-negotiable review questions.

This phase changes governance documentation only. Runtime, Tool, Skill, Domain,
CLI, and test implementation are unchanged.

## 2. New Project Identity

Agonionce is now explicitly defined as an **AI-assisted CTF research and
security learning framework**. Its valid uses are authorized CTF competitions,
local CTF laboratories, security coursework, explicitly permitted security
research, and defensive security experimentation.

The governance rejects characterization as a network attack tool and excludes
unauthorized targets, real-world attack automation, unknown-system scanning,
and exploitation without permission. Its central model is reasoning plus
knowledge plus controlled execution plus evidence-based learning.

## 3. Architecture Governance

The constitution defines six layers: Runtime, Intelligence, Domain, Skill,
Execution, and Environment. It assigns one clear responsibility to each and
adds explicit boundaries among Runtime, Skill, Tool, and future MCP
connections.

Runtime controls how the agent operates. Skills describe how it reasons about a
domain. Tools define what it can execute. MCP may connect future tools but is
neither the agent brain nor a replacement for skills. All executable actions
must pass through ToolRuntime, PolicyEngine, and ApprovalManager and return a
normalized observation.

New features must document their purpose, owning architecture layer, security
boundary, deterministic tests, and local demo. The required development order
is contract definition, minimal implementation, deterministic testing, local
demonstration, and only then controlled real-environment integration.

## 4. Security Boundary

All CTF activity must be authorized, scoped, controlled, and auditable. Local
fake challenges, labs, Docker environments, VMs, and sandboxes take precedence
over remote integration. Public targets are denied by default, and unknown
systems must not be scanned or probed.

The update explicitly prohibits bypassing ToolRuntime, PolicyEngine,
ApprovalManager, or workspace isolation. It also prohibits hidden execution in
skills, prompts, domain runtimes, adapters, or MCP connections. Sensitive
configuration, credentials, logs, private checkpoints, challenge secrets, and
user attachments remain outside version control.

## 5. Future Roadmap

R5 Web Runtime Foundation is recorded as the completed foundation. The domain
roadmap continues through Web, Pwn, Reverse, Crypto, and Misc runtimes. Each
mature domain is expected to have separate Runtime, Skill, Tools, and
Intelligence components.

MCP is documented as a future connection protocol behind the established
execution controls. Experience learning is explicitly marked **NOT
IMPLEMENTED** and is planned as structured experience memory plus governed
knowledge evolution, potentially using an Experience Store, Knowledge Graph,
Pattern Library, and controlled Skill Evolution. Direct model-weight
modification is not part of this direction.
